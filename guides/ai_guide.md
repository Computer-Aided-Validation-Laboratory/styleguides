# Computer Aided Validation Lab: Guide to Agentic AI for Software Development

## Overview

Agents are particularly effective at exploring a codebase, proposing & prototyping multiple designs, implementing repetitive changes, writing tests and performing preliminary reviews. However, they can also produce code that works but is unnecessarily complicated, inconsistent with existing conventions or extremely inefficient. Engineers generally have a better feel for what is going to be cohesive with the rest of the codebase and what will result in the best performance. If an engineer is unsure which path to take agents are useful for quickly exploring both options and providing benchmark data before proceeding down a concrete path.

It should be emphasised that for performance critical and user facing code it is essential to **read, review & refactor the code** generated by the agent.  

Generally, the most effective workflow for working with AI agents is iterative through the following stages where a loop back to a previous stage can happen at any point: investigate, evaluate options, implement, independently verify, benchmark and review. Some tips are given below for how to get the most out of using agents when developing code in our lab. 


## 1. Investigate before implementing

Start by explaining the problem. If you have an idea for what the solution might look like decribe this including your reasoning as to why you think this solution will work but try not to be extremely prescriptive you want to give the agent some freedom to inspect the code and improve on your suggestions. An example prompt for a refactor is given below:

**Example prompt:**

> Naming of types throughout the codebase is inconsistent. For example, X in file Y and Z in file W follow different conventions. Investigate the relevant code, identify the inconsistencies and propose several approaches to resolving them. Do not modify the code yet.


## 2. Request design alternatives

Do not simply ask the agent to design a feature and implement its preferred solution directly. 

**Example prompt:**

> Investigate this problem and give me several design options, including their advantages, disadvantages and implications for performance and maintainability. I will decide how we proceed.

Agents often recommend designs that will work but do not match the intended architecture or design priorities. Asking for multiple alternatives allows you to review and select the best option to fit the design requirements (which could be a hybrid combination of options). 

You might need to iterate through this stage with several prompts asking the agent to update the design based on your requests until you are happy.

If this is an extremely large feature it can be useful to ask the agent to save the complete design plan into a markdown file that you can review separately before allowing the agent to implement the design.

## 3. Ask for clarifying questions before implementation

Once you have outlined a design for a proposed feature, ask the agent to investigate it against the existing codebase and identify anything you have overlooked.

**Example prompt:**

> Here is my proposed design: [description/plan.md]. Investigate this against the existing codebase and ask any clarifying questions before we begin. Do not implement anything yet.

This frequently reveals missing requirements, unexpected dependencies or assumptions that need correcting. Always review the agent's recommended answers to these questions. They may not reflect what you actually want.

## 4. Establish independent verification

**Never rely on an agent telling you that its implementation works.**

Establish a way of checking correctness independently of the implementation. It is always best if the agent can implement the feature and check its own work while it is doing so. A robust test suite or method of idependently checking correctness is absolutely essential. 

Preferred checking approaches include:

- **Analytical verification:** Compare outputs against known mathematical or physical solutions. This is particularly valuable for scientific software.
- **End-to-end regression testing:** Compare results against independently established reference or *gold* outputs.
- **Unit and integration testing:** Exercise edge cases, invariants and interactions between components.

Establish the verification cases before implementation. Review the test inputs, expected outputs and tolerances carefully. An agent-generated test that simply reproduces the same incorrect assumptions as the implementation is not independent verification.

**Beware**: sometimes agents will modify test tolerances or test output to force tests to pass. Make sure you verify that the agent has not bypassed the tests.

## 5. Benchmark once correctness is established

After the implementation passes verification, ask the agent to create and run performance benchmarks. Compare the new implementation against the existing development (dev) branch or previous implementation wherever possible.

**Example prompt:**

> Create a reproducible performance benchmark for this feature. Run it against the current implementation and the previous implementation in dev, using equivalent inputs and conditions. Report any performance regressions and save the results as a baseline for future comparisons.

## 6. Use agents for repetitive plumbing

Agents are particularly useful for routine engineering work, including test harnesses, benchmark orchestration, build configuration and repetitive integration code.

It is often unnecessary to manually inspect every line of straightforward boilerplate.

Instead, focus your review on whether the resulting tests and benchmarks exercise the right functionality, use meaningful inputs and check sensible outputs.

Review effort should reflect the consequences of an error, rather than being distributed equally across every file.

## 7. Run an independent style and quality review

Keep project conventions documented in a style guide and reference them through `AGENTS.md`.

Before your own detailed review, consider using a **fresh agent with minimal context** to review the changes against those conventions.

**Example prompt:**

> Review the changes on this branch against the project style guide and existing code conventions. Identify unnecessary abstractions, duplication, inconsistent naming, avoidable allocations and overly complicated implementations. Do not modify any files. Report findings with file and line references.

A fresh agent can identify problems that the implementing agent overlooks or has implicitly accepted. It can also be useful to use an agent from a different provider for independence of the review.

Style compliance still needs human judgement. Agents can be inconsistent across languages and may introduce unnecessary Python abstractions, defensive code or other complexity. 

Agents can also add a bunch of unecessary compatibility shims when breaking changes are intended in the codebase and they also have a tendency to leave behind a bunch of dead code during refactors. Specifically ask the agent to do a dead code sweep as part of its review.

## 8. Review core code file by file

For performance critical code, public APIs and user facing functionality, conduct a deliberate manual line by line review after the initial implementation is working.

Look for:

- Unnecessary abstractions, indirection or complexity.
- Poor naming and inconsistent interfaces.
- Duplicate code or redundant state.
- Unnecessary memory allocations or unecessary computations.
- Inefficient algorithms and missed opportunities for vectorisation.
- Unclear control flow, hidden assumptions and difficult to maintain code.

The initial implementation should always be treated as an **exploratory prototype** not a mergable production feature. Make sure you actually **read the code** when it hits one of our key principles:

1. Make it correct
2. Make it fast
3. Make it easy for users

## 9. Generate a call graph guided review document

A normal Git diff shows what changed, but does not necessarily explain how the new feature works and how the data flows through the code for the new feature.

Ask the agent to compare the feature branch against the development branch, trace the new feature through the call graph and produce a Markdown review document.

**Example prompt:**

> Compare my current branch against `dev`. Trace the call graph and data flow for the new feature, identifying the relevant entry points, functions, types and dependencies. Generate a Markdown review guide that explains the execution flow and identifies the changed files and line ranges in the order they are encountered. Save this for a file-by-file review. Do not modify the code.

This provides a much more useful review narrative than a diff alone, particularly for changes involving multiple layers of the codebase.

Treat the generated guide as a navigation aid and check that it has not omitted important code paths.

## 10. Batch review comments and refactors

During manual review, record problems as concise bullet point notes, just as you would when reviewing a colleague's pull request.

Rather than asking the agent to fix every minor issue individually, collect a meaningful batch of related changes.

**Example prompt:**

> Implement the following review comments as a single coordinated refactor:
>
> - Rename type X to Y consistently throughout the codebase.
> - Remove redundant state W from component Z.
> - Simplify function A by removing B to avoid repeated calculations.
> - Replace the unnecessary abstraction in file B as there are only two concrete types.
>
> Preserve existing behaviour and public APIs unless explicitly noted. After making the changes, run the relevant tests and report any failures.

Batching related fixes reduces repeated agent interactions and allows the agent to handle coordinated renames and interface changes together.

After each batch, rerun the relevant verification tests. Repeat the review and refactor cycle until the code is clear, maintainable and performant.
